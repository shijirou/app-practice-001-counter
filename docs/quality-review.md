# 品質チェックの記録

品質チェックの結果を、日付ごとに下へ書き足していく。やり方は、全アプリ共通のスキル `quality-check`。
見つけたものは3つに分ける: **まちがい**（要件・ドキュメントとのずれ、不具合）／**標準から外れている**（React などのふつうのやり方と違う）／**今後の改善**（今は困らないが、使い方が変わったら直したい）。

## 2026-11-14（1回目・Issue #13）

第三者のレビュアーの立場で、完成したアプリを検査した。

### 結果の表
| 項目 | 結果 |
|---|---|
| lint（oxlint 1.93.0） | 0件。jsx-a11y（使いやすさ）と exhaustive-deps を足した厳しい設定でも 0件 |
| ビルド（Vite 8.3.8） | 成功 |
| 部品の版・脆弱性 | `npm outdated` は空（すべて最新）、`npm audit` は 0件。[技術スタック](tech-stack.md)の表と一致 |
| 動作確認（本物のブラウザを自動で操作） | 直す前: 約60項目のうち NG が 4種類。直したあと: NG 0件 |
| 自動テスト | **ない**（今後の改善 I-1 → 2026-11-14 に Vitest で足した。22 件） |
| 見つかったもの | まちがい 4件／標準から外れている 5件／今後の改善 6件 |

動作確認の道具: Playwright-core 1.65.1 と Chromium 156（作業用フォルダに入れただけで、リポジトリには入れていない）。画面幅は 320〜1920px の6種類で試した。

### 全体の評価
- 要件定義書の機能 F1〜F7 は、すべて書かれたとおりに動いた（加算・減算・0 の下限・直接修正・Enter での確定・リセットの確認・保存・商品名 50 文字）。
- データ設計とも一致した（保存キーは `counter.count` と `counter.productName` の2つだけ、上限 999999999、壊れた保存値は 0 扱い、保存できない環境でも動く）。外部への通信もなかった。
- 部品の分け方（保存の仕組みを `useStoredState` に切り出す）や、ラベルと入力欄のつながり、`aria-live`、フォーカスの見やすさはよくできている。
- 弱いのは、**実際の使い方（タブレットの横置き・2つのタブ・大きな数字）を試していなかった**こと。要件の「完成の目安」にある「タブレットの画面幅で崩れずに使える」を、確認しないまま完成にしていた。

### まちがい
| # | 場所 | 内容 | なぜ問題か | どうしたか |
|---|---|---|---|---|
| M-1 | README の先頭 | 題名が「（アプリ名）」、説明が「（1〜2行で…）」のままだった | 見た人に何のアプリか伝わらない。ひな形の書きかけが残っていた | 題名と説明を書いた |
| M-2 | `App.css` | タブレットの横置き（1024×768）で、大きな＋1 ボタンが画面の下にはみ出し、スクロールしないと押せなかった（9桁のとき。下端 831px、画面の高さ 768px） | 主役のボタンが見えない。要件の「親指で押しやすい位置」「タブレットで使える」に反する | 画面が低いときは余白をつめ、数字の大きさを画面の高さにも合わせた。1024×700 でも収まる |
| M-3 | `App.css` | 7桁以上の数字が途中で折り返された（768px 幅で「999999／999」の2行になる） | 数え間違いを減らすためのアプリで、数字が2行に割れると読み間違えやすい | 桁数に合わせて文字を小さくし、折り返さない（`white-space: nowrap`）。9桁でも1行 |
| M-4 | `useStoredState.js` | 2つのタブで開くと、あとから押したほうが古い数を元に足し、もう一方の分が消えた（A で＋2、B で＋1 → 3 のはずが 1） | 数え間違いの原因になる。タブレットでアプリを2つ開いてしまうのはありえる | 別のタブの変更を受け取って反映する（`storage` イベント）。3 になるのを確認 |
